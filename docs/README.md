# DataStory Studio — story data

Public data for the [DataStory Studio](https://apps.apple.com/app/id6800584845)
iOS app. Every
file here is served straight from this branch by GitHub Pages, so
pushing to `main` is the whole deploy.

Nothing here is generated by hand. Edit the datasets in the app repo under
`DataStoryStudio/Resources/`, run `Tools/gen_manifest.py`, and copy the contents
of `remote/` into this repository.

## What the app does with this

1. On launch — at most once every six hours — it fetches `manifest.json`.
2. If `version` has not moved since the last check, it stops there. That request
   is about 1.4 KB.
3. If it has, it downloads only the datasets whose own `version` has changed.
4. Those are cached on the device and layered over the copies shipped inside the
   app.

## manifest.json

```json
{
  "schema": 1,
  "version": 7,
  "datasets": [
    { "id": "gdp", "version": 3, "path": "Race-gdp.json", "bytes": 18244 }
  ]
}
```

| Field | Meaning |
|---|---|
| `schema` | Format version of this file. A build ignores a catalog whose schema is newer than it understands, so new fields can be added without breaking installed apps. |
| `version` | Bumped whenever any dataset changes. Lets the app skip everything else when nothing has moved. |
| `datasets[].id` | Must match the `id` inside the dataset file. A mismatch is rejected. |
| `datasets[].version` | Bumped only for datasets whose contents actually changed, so one edit does not re-download all nine. |
| `datasets[].path` | Relative to this file. |
| `datasets[].bytes` | Exact file size. A download that does not match is discarded — truncated responses are the common failure and they are silent. |

`_fingerprints` is publishing bookkeeping. The app's decoder ignores it.

## app.json — supported versions

Separate from `manifest.json`, and hand-edited. The two change on different
schedules — the catalog when the data changes, this when a release goes out —
and sharing one file would mean a story edit and a forced upgrade shared a
version number.

```json
{
  "schema": 1,
  "minimumVersion": "1.0.1",
  "latestVersion": "1.2.0",
  "message": null,
  "appStoreID": null
}
```

| Field | Meaning |
|---|---|
| `schema` | Format version. A build ignores a file whose schema is newer than it understands — it will not guess at fields it may be reading wrong. Omitting this reads as `1`. |
| `minimumVersion` | Builds below this are **blocked** behind a full-screen gate with no way past. Omit, or leave `null`, to block nobody. |
| `latestVersion` | Builds below this see a dismissible bar. Dismissal is remembered per version, so the next release still gets to speak. |
| `message` | Replaces the default explanation on the blocking screen. `null` uses the standard wording. |
| `appStoreID` | Numeric App Store ID, so the Update button can be pointed at a live listing without shipping a build. Falls back to `AppInfo.appStoreID`. Non-numeric values are ignored and the button hides. |

Versions are compared component by component as integers, so `1.10.0` is
correctly newer than `1.9.0`, and `1.2` and `1.2.0` are the same version.

**`minimumVersion` locks people out of the app. Treat it that way.**

- Set it to a version that is actually live on the App Store and propagated.
  Pointing it at a build still in review leaves everyone stuck with an Update
  button that shows *Open*.
- The verdict is cached on the device, so a device that has read this file once
  stays gated even offline — that is deliberate, or the gate would be defeated
  by aeroplane mode. The corollary is that a mistake here is not fixed by
  reverting alone: affected devices need one more foreground with a network to
  pick up the correction.
- A device that has *never* successfully fetched this file is never gated, so a
  fresh install with no network still opens.
- Every failure to fetch is silent and changes nothing.

## Rules the app enforces

- **This data can add or update a story. It can never remove one.** The copies
  inside the app are the floor, so a bad push means "no new data", never "the
  app is empty".
- Downloaded files are decoded and sanity-checked *before* being cached. A file
  that will not parse, has the wrong `id`, or has fewer than two entities never
  reaches the device's library.
- HTTPS only.
- Every failure is silent. No network, repo renamed, GitHub down — the app opens
  on its bundled stories and says nothing.

## Adding a new story

1. Put `Race-<something>.json` in `docs/`.
2. Validate it **before** pushing:

   ```sh
   python3 Tools/check_dataset.py docs/Race-something.json
   ```

   The app rejects malformed data silently — no error on screen, just a line in
   the device log — so a file that is wrong simply never appears. This catches
   it first.

3. Regenerate the manifest and push. The generator adds the entry and sets
   `version: 1` for you; do not hand-edit `manifest.json`.

### New categories

The `category` field can be anything. A value this build does not recognise —
`music`, `health`, whatever — is not an error: the story downloads, appears
under **More**, and works normally. Giving that category its own name, icon and
colour needs an app release, but the *data* does not have to wait for one.

Recognised today: `economy`, `population`, `technology`, `energy`, `military`,
`sport`. Everything else groups under **More**.

## Publishing an update

```sh
# in the app repo
python3 Tools/gen_manifest.py

# then, in this repo — note docs/, which is what Pages publishes
cp -R /path/to/DataStoryStudio/remote/docs/. docs/
git add -A && git commit -m "Update GDP through 2026" && git push
```

Version numbers are derived from file fingerprints, so re-running the generator
without changing anything bumps nothing and costs users no downloads.

Allow about five minutes for the GitHub Pages CDN to catch up.

## Sources

Figures come from the published sources credited inside each dataset's
`source` and `sourceURL` fields. Years between anchor points are interpolated,
which is how animated charts of this kind are normally built — treat them as
illustrative rather than exact.
